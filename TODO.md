## Валідація відповідей API

- Розбирати кожну відповідь через ky `.json(schema)`. `.json<T>()` — це приведення типу без перевірки, lint його не ловить.
- Щоб зміни бекенду не ламали фронт:
  - використовувати `z.object`, а не `z.strictObject`: невідомі поля просто відкидаються, тож нові поля на бекенді нічого не ламають;
  - описувати лише ті поля, які фронт справді використовує;
  - для некритичних полів ставити `z.catch(значення)`, наприклад для нового статусу, якого фронт ще не знає.
- Несумісні зміни бекенду робити в три кроки (expand → migrate → contract): додати нове поле поруч зі старим → перевести фронт на нове поле → прибрати старе. Для великих змін — нова версія API (`/v2`).
- Старі вкладки SPA після деплою працюють зі старим JS годинами й днями. Бекенд має підтримувати і старий фронт. Фронт може перевіряти, чи вийшла нова версія, і пропонувати перезавантажити сторінку.
- Коли з'явиться реальний бекенд:
  - генерувати zod-схеми з OpenAPI (orval, hey-api), щоб несумісна зміна контракту падала на `typecheck` у CI;
  - якщо бекенд на TypeScript в одному репозиторії, натомість взяти спільні типи (tRPC, oRPC).
- Надсилати `SchemaValidationError` у моніторинг (Sentry) разом з endpoint і шляхом поля. Помилки з `createRoot` (`onUncaughtError`, `onCaughtError`, `onRecoverableError`) збирати в одну функцію `reportError`.
